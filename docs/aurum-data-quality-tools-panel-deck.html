The tool is the inspector
It checks the data and reports PASS or FAIL for each rule. That is all it does.
Aurum is the decision maker
Aurum decides: hold the load, quarantine rows, retry, send an alert, or promote to Silver.
One rule we never break: if the tool crashes or cannot connect, the result is CHECK DID NOT RUN. It is never a pass.

Group 1 · Free software we run · 1 of 6
Soda Core
Readable rules, run against our database.
What it is
A free tool where we write checks in simple text, like “missing fund_symbol = 0”, and it runs them on the database.
Where it sits in Aurum
Connects to Bronze PostgreSQL, returns PASS or FAIL for each rule. Aurum then decides if the load moves to Silver.
Good for us
+
Rules are easy to read, even for non-coders
+
Rule files live in Git next to Aurum code
+
Fits our PostgreSQL-first setup directly
Watch out
−
It does not decide anything. Quarantine, retry, alerts and storing results are still ours to build
−
Very custom Python logic is easier in GX
−
Version 3 and 4 differ, so we pick and pin one
Remember
Soda is a lightweight check engine: readable rules on PostgreSQL, and Aurum uses the result to decide Bronze to Silver.
Group 1 · Free software we run · 2 of 6
Great Expectations (GX Core)
Reusable Python checks with reports.
What it is
A Python library. We group checks, called Expectations, into Suites, run them, and get results plus Data Docs web pages.
Where it sits in Aurum
Connects to PostgreSQL, runs the price-table suite, and returns the failed checks for Aurum to judge.
Good for us
+
Full Python control for unusual logic
+
Reusable suites, and Data Docs show rules and results
+
Strong when rules get complex
Watch out
−
More ideas to learn: Context, Asset, Batch, Suite, Checkpoint
−
More setup than Soda
−
We still schedule runs and host Data Docs
Remember
GX is a flexible Python toolkit. More power than Soda, and more setup.
Group 1 · Free software we run · 3 of 6
dbt tests
Quality checks inside a dbt project.
What it is
dbt builds tables with SQL. Its tests (not_null, unique, accepted_values, relationships) check data next to the models.
Where it sits in Aurum
A test on the Bronze source can stop the Silver model from building. This only works if Aurum uses dbt.
Good for us
+
Built-in tests cover the basics
+
Checks live beside the SQL that builds tables
+
With dbt build, a failed upstream test skips dependent models
Watch out
−
Adopting dbt only for a few checks is too much
−
dbt test alone does not undo a table already built
−
store_failures saves bad rows, but it is not quarantine
Remember
dbt tests are a good fit only if Aurum already builds Silver with dbt.
Group 1 · Free software we run · 4 of 6
Deequ
Quality checks for data in Spark.
What it is
An Amazon open-source library. It checks Spark DataFrames, which are Spark's tables, and returns metrics and pass or fail results.
Where it sits in Aurum
Spark reads PostgreSQL over JDBC, then Deequ checks the DataFrame. Only makes sense if Aurum already uses Spark.
Good for us
+
Built for very large data
+
Also profiles data and suggests checks
+
Can keep metrics over time
Watch out
−
Needs Spark, Java and matching versions (2.1.0 and later needs Java 11)
−
Adds many moving parts to a PostgreSQL-first design
−
75.7M rows alone does not prove we need Spark
Remember
Deequ is for Spark users. It is not our first choice while Aurum is PostgreSQL-first.
Group 1 · Free software we run · 5 of 6
Elementary OSS
Trend watching for a dbt project.
What it is
An add-on for dbt. It saves metrics from each run and compares today with history, to spot odd volume, freshness or column changes.
Where it sits in Aurum
If a reload gives 40M rows when it normally gives about 75M, it can flag the drop, once it has enough history.
Good for us
+
Catches problems no one wrote a rule for
+
Adds volume, freshness and column checks
+
Gives reports and alerts
Watch out
−
Needs a dbt project and enough history
−
Weekends, holidays and partial loads can cause false alarms
−
Failed tests only block if we set that up
Remember
Elementary is a trend watcher that adds to dbt. It does not replace our rules.

Where it sits in Aurum
Manjula opens mutual_fund_prices and sees who owns it, its columns and its quality results.
Good for us
+
Catalog and quality in one view
+
Shows owners and column descriptions
+
Profiles data and runs tests on a schedule
Watch out

A platform with several services to run
−
PostgreSQL does not give us every lineage link for free
−
Feeding results into the Silver gate needs our own integration
Remember
OpenMetadata is for visibility and ownership. It is heavier than a check library.

Group 2 · Cloud services · 1 of 3
AWS Glue Data Quality
AWS runs the data quality checks.
What it is
A managed AWS service. We define rules, AWS runs them and returns the results. There is no engine for us to host.
Where it sits in Aurum
Two routes: Data Catalog (tables in the Glue Catalog) or an ETL job (checks inside a Glue job). We choose the route first.
Good for us
+
Nothing to install or host
+
Natural if the client is already on AWS
+
ETL job route works with sources Glue jobs can read
Watch out
−
Catalog route: JDBC is supported (Lake Formation off), but Amazon RDS and Aurora are not
−
Managed is not zero setup: IAM, network, a Glue connection, cost
−
Confirm the exact route before we design
Remember
Glue has two routes. Pick the route first, especially if our PostgreSQL runs on RDS or Aurora.

Group 3 · Always watching · 1 of 3
Monte Carlo
Watches the data and alerts when it looks odd.
What it is
A commercial monitoring platform. It learns normal behavior for volume, freshness and schema, then alerts on unusual changes.
Where it sits in Aurum
A reload drops from about 75M to 40M rows. Every row may still pass the rules, but Monte Carlo can flag the drop.
Good for us
+
Catches problems we did not write rules for
+
Also supports custom SQL and validation rules
+
Documented PostgreSQL integration
Watch out
−
Opt-in row-count monitors run count(*) on the table, so measure the load
−
Lineage is not marked as supported for PostgreSQL
−
A large commercial platform, so we must prove the value
Remember
Monte Carlo is a health monitor, not only a rule checker. Test it after the basics work.
Group 3 · Always watching · 2 of 3
Anomalo
Learns what normal data looks like.
What it is
A commercial tool that learns from history and flags unexpected changes inside the data itself. It also runs normal rules.
Where it sits in Aurum
Row count looks normal, but the price values shift a lot. A row count check passes. Anomalo can flag the change.
Good for us
+
Spots value-level changes, not just counts
+
No-code rules and custom SQL
+
Profiling and root-cause context
Watch out
−
Needs about 2 weeks of runs, better after 30 to 60 days
−
Table should have at least 100 rows a day
−
PostgreSQL is listed, but the docs are private, so verify in a pilot
Remember
Anomalo finds surprises we did not predict, but it needs history and a pilot. No public price was found.
Group 3 · Always watching · 3 of 3
Bigeye
Tracks data health numbers over time.
What it is
A commercial tool that tracks numbers like row count or null percent over time, and alerts when they move outside normal.
Where it sits in Aurum
Connects to PostgreSQL with a read-only user, profiles the tables, and suggests metrics for mutual_fund_prices.
Good for us
+
Documented PostgreSQL setup with a read-only user
+
Agent option runs inside our own network
+
Custom Rules and Join Rules, like symbol exists in mutual_funds
Watch out
−
Profiling and metrics run queries, so measure the load on 75.7M rows
−
PostgreSQL is not in its lineage connector list
−
Much broader than a Bronze to Silver checker
Remember
Bigeye watches health numbers over time. Confirm PostgreSQL lineage in a pilot.

Group 4 · Big platforms · 1 of 4
Informatica Data Quality
Quality rules inside a big governance platform.
What it is
Part of Informatica's cloud platform. A rule template links to a governed definition, and each data element gets a score.
Where it sits in Aurum
A fund_symbol completeness rule scores mutual_fund_prices as Good, Acceptable or Not Acceptable. Aurum reads the score.
Good for us
+
Rules connect to the catalog and glossary
+
Scores in three bands, scheduled daily, weekly or monthly
+
Fits clients that already own Informatica
Watch out
−
The rules page does not name PostgreSQL. JDBC is listed, so confirm with Informatica
−
Consumption-based pricing, so no simple price
−
A platform choice, not just a validator
Remember
Informatica only makes sense if the client already uses it. Confirm PostgreSQL first.
Group 4 · Big platforms · 2 of 4
Talend Data Quality (Qlik)
Quality steps built into ETL jobs.
What it is
Qlik bought Talend in May 2023. We design jobs in Talend Studio, and quality steps are components inside the job.
Where it sits in Aurum
tPostgresqlValidRows and tPostgresqlInvalidRows read PostgreSQL and split rows that match or break a pattern.
Good for us
+
PostgreSQL components are documented
+
Splits good and bad rows inside the job
+
Talend Cloud has a Trust Score from 0 to 5
Watch out
−
A different style from Soda and GX: logic lives in jobs
−
Some components need the Feature Manager
−
Heavier than a small YAML layer
Remember
Talend fits clients who already build their pipelines as Talend jobs.
Group 4 · Big platforms · 3 of 4
Collibra Data Quality
Enterprise quality with simple scores.
What it is
An enterprise data quality platform. Each dataset gets a score: 90 to 100 is pass, 76 to 89 warning, 0 to 75 fail.
Where it sits in Aurum
Aurum reads the score as evidence, but still decides what pass, warning and fail mean for release.
Good for us
+
Simple pass, warning, fail view
+
PostgreSQL documented for Classic and Cloud
+
Natural for clients that already use Collibra
Watch out
−
Classic and Cloud are separate apps with separate docs
−
No PostgreSQL pushdown: Classic says No, Cloud says Pullup
−
Pin the release, because driver versions change
Remember
Collibra: say Classic or Cloud first, and pin the release.
Group 4 · Big platforms · 4 of 4
Ataccama ONE
Quality, catalog and monitoring in one platform.
What it is
An enterprise platform that combines data processing, quality rules, catalog controls and observability.
Where it sits in Aurum
For mutual_fund_prices it can monitor quality results, volume, statistical anomalies, schema changes and freshness.
Good for us
+
PostgreSQL is a supported connector
+
Rules and monitoring in one place
+
A glossary is optional: rules can map straight to attributes
Watch out
−
No PostgreSQL lineage, and pushdown only for Snowflake and Databricks
−
Freshness needs track_commit_timestamp = on and a restart
−
Sample profiling must run first
Remember
Ataccama is an all-in-one platform for clients who already own it.

Our suggestion
Test Soda and GX first.
They talk to PostgreSQL directly, they are free, and they are easy to compare on the same data.
Everything else is a later step, or a fit for a client who already uses that platform.
This is a fit decision from the documentation. It is not a benchmark saying one tool is best.
What the test would look like
Same data, same rules, three situations
1. Clean load
PASS
Rules run and all pass.
2. Bad load
FAIL
Missing symbol, repeats, bad price are caught.
3. Tool cannot run
CHECK DID NOT RUN
Never treated as a pass.
We compare Soda and GX on
+
Easy to connect
+
Easy to maintain
+
Shows which rows failed
+
Handles custom rules
+
Runtime and database load
+
Keeps Aurum simple
Start with a small load, then run the chosen setup at real scale, 75.7M rows. Keep run IDs in the evidence.
